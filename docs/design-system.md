The product is used all day by non-technical office staff, often with a Student sitting across the desk. Every rule below serves that: big, calm, one job per screen, and the same look and behaviour everywhere.

## Non-negotiable rules

1. **Components use tokens only.** No hex, rgb or named colours, pixel sizes or shadows written inside a component. Everything comes from the tokens below. CI fails on a raw colour outside the token file.
2. **One theme for every office: Ivory**, light and dark (see Theming). Cream pages and burgundy actions, the colours of a rudraksha bead. Offices no longer choose colours; each person still chooses light or dark.
3. **Status colours are fixed, and colour means one thing.** Good (green), warning (amber) and problem (red) have one light set and one dark set, so "Rejected" or "Overdue" means the same everywhere. Money and progress bars use the good green. Red is only for a problem. The accent is never a status (the burgundy sits too close to the problem red): a status that is simply in progress (Applied, Offer, Starts on..., New visitor) is ink with a hollow ring, a Normal priority is a hollow ring and Low a quieter one (ticket 21).
4. **Readable text is guaranteed, not hoped for.** Every text token reaches WCAG 2.2 AA (4.5:1) on the sheet and on the page itself (titles, sub-lines and counts sit on the page colour). A test checks it; the Ivory caption grey was darkened from the prototype's `#8f847c` to `#766c65` to pass.
5. **Dark mode has its own values.** A warm near-black page (`#121110`) and panel (`#1a1817`), cream text and a soft burgundy accent. It is never a saturated dark blue or brown.
6. **Colour is never the only signal.** Every status also has a word or an icon (for example a "Rejected" chip, an "Overdue" label).
7. **Line icons from one set.** No emoji in the interface.
8. **An action never moves the person.** Approving, saving, deleting, switching a tab, ticking a box or closing a dialog keeps the page where it was: same scroll position, and focus back on the control that was used (or, if it is gone, the nearest control for the same item). Update data in place (React Query cache, local state); never remount the page, reset scroll or navigate for an action that stays on the same page. The same holds inside dialogs and sheets: redrawing a dialog (switching its tabs, ticking, removing an item, coming back after "Are you sure?") keeps each scrolled area where it was. Only opening another page starts at the top. Component tests check that focus stays after the action (product owner, 2026-11-18). When the control that was used is gone, the cursor is moved with `useFocusAfterChange`, which runs once the change is on screen, never with a timer (a timer can fire before the screen changes, and the cursor is then lost). Tabs that switch the body of a page (Employees: People / Working hours; Documents: Students / Bin) stay mounted in one place, so the pressed tab keeps the cursor; a tab that reads its data again after a save (a Student's Fees) keeps what it shows while it reads (ticket 20). A Student's Activity does the same after the Note or the Priority is saved: its first pages are read again and what is new is added to the timeline, which is never taken away; older entries already shown stay, and when it can't be read again it keeps what it shows (ticket 25).
9. **No box around every control** (Ivory, 2026-11-24). One filled button per screen area, for the main action; every other button is words with an icon and no box. Tabs and switches are words with an underline. A status is a dot and a word, never a filled badge. A section's content sits on one white sheet (see Sheets), so what belongs together is seen at once; nothing inside a sheet gets a box of its own. Other boxes are only for popups, menus and the fields you type into.
10. **Padding holds** (ticket 21). Nothing inside a sheet or popup is closer to its sides than 18 (14 on phones) or closer than 10 to its top and bottom; blocks of a page are at least 16 apart. A note or a banner that shares a section with a sheet is a block too: 16 from the sheet, never the 10 between a section's title and its sheet (ticket 25).

## Tokens

All tokens are CSS custom properties set on `<html>`. Tailwind 4 maps them through `@theme inline`, so classes such as `bg-paper` and `text-ink-2` resolve to tokens.

### Colour (semantic, themed)

| Token                                                                                                          | Used for                                                                                       |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `--paper`                                                                                                      | Sheets, dialogs, inputs                                                                        |
| `--canvas`                                                                                                     | Page background                                                                                |
| `--fill`, `--fill-2`                                                                                           | Table headers, hovers, quiet backgrounds, empty progress tracks                                |
| `--rule`, `--rule-2`                                                                                           | Lines between rows (ink 15% light, 17% dark); `rule-2` for inputs                              |
| `--sheet-rule`                                                                                                 | A sheet's border: `--rule` in light, ink 13% in dark                                           |
| `--band`, `--row-hover`                                                                                        | The band under column heads (`--fill` 55% into `--paper`); a row under the pointer (60%)       |
| `--bead-1` to `--bead-5`                                                                                       | The thread's five shades, Lead to Visa (see The thread)                                        |
| `--ink`, `--ink-2`, `--ink-3`                                                                                  | Main text, secondary text, captions (each at least 4.5:1 on `--paper` and `--canvas`)          |
| `--accent`, `--accent-hover`, `--accent-ink`, `--tint`                                                         | Primary buttons, links, progress, selected items; text on the accent; light accent backgrounds |
| `--side-bg`, `--side-ink`, `--side-muted`, `--side-hover`, `--side-active`, `--side-active-ink`, `--side-rule` | Sidebar                                                                                        |

### Colour (fixed, not themed)

`--good`, `--good-tint`, `--warn`, `--warn-tint`, `--bad`, `--bad-tint`, `--note`, `--note-rule`, and `--gold` (a small mark of value, such as beside a high-priority Student). These have one light set and one dark set (Ivory: good `#3f6b3a` / `#8fbf85`, warning `#94570f` / `#e0a85c`, problem `#9b2226` / `#e88a85`).

### Colour (charts, fixed, not themed)

`--c1` blue `#2a78d6`, `--c2` orange `#eb6834`, `--c3` green `#1baf7a`. Dark mode: `#3987e5`, `#d95926`, `#199e70`. Always used in this order. They passed colour-blind separation checks on white and on the dark panel. Charts never use the theme accent or the status colours for series. A single-series bar list may use `--accent`. Every chart has a legend (two or more series), a hover/focus tooltip with exact values, and a "Show as a table" view (see Chart section). One y-axis only.

### Type

One family: Geist (fallback: system UI). Figures use tabular numbers. Page titles, dialog titles and big figures use weight 500 with slightly tight letter spacing (-0.025em); section titles -0.01em. Titles balance their lines (`text-wrap: balance`).

**One scale** (ticket 21): the sizes are 12, 13, 14, 15, 16, 18, 20, 24, 28 and 32, and the weights 400, 500 and 600. Nothing else exists (a test reads `globals.css` and fails on any other size or weight). Bold in the content is at most 600; a task's title is 500. Sizes come from `--size-*` tokens that take their phone values at 640 and below, so components never pick a size per width.

| Role                                   | Computers (above 640) | Phones (640 and below) | Weight |
| -------------------------------------- | --------------------- | ---------------------- | ------ |
| Page title                             | 28 / 34               | 24 / 30                | 500    |
| Section title                          | 18 / 24               | 18 / 24                | 600    |
| Dialog title                           | 24 / 30               | 24 / 30                | 500    |
| Page text, table cells                 | 16 / 24               | 15 / 22                | 400    |
| A name in a list (`text-name`)         | 18 / 24               | 16 / 22                | 600    |
| The line under it, chips               | 15 / 22               | 14 / 20                | 400    |
| Column heads, captions, small text     | 14 / 20               | 13 / 18                | 500    |
| Buttons (small buttons)                | 15 (15)               | 15 (14)                | 500    |
| Figures                                | 32 / 40               | 24 / 30                | 500    |
| Email list: the Student's name         | 20 / 26               | 18 / 24                | 600    |
| Configuration › Universities: the name | 20 / 28               | 16 / 22                | 600    |
| Fields you type into (`text-input`)    | 16                    | 16 (iOS never zooms)   | 400    |

Labels never look like their values: a field's label is 15 (14 on phones), weight 500, in `--ink-2`.

Sentence case everywhere. No all-caps labels.

### Spacing, size and shape

- **Spacing scale:** 4, 8, 12, 16, 20, 24, 32, 40, 48. Sections are 32 apart; items in a group are 16 apart.
- **Control height:** 44 (buttons, inputs, selects, segmented controls). Small buttons are also 44 tall, with less padding and smaller text. Large primary actions 52. Side menu items 66 in the strip and 48 in the slide-out menu. Icon buttons (theme, notifications, search, your initials) are 44 square. A checkbox or radio may draw at 22, but the area that toggles it is at least 44 square (a row checkbox fills its table cell). Link buttons and breadcrumbs are 44 tall too.
- **Table rows:** at least 56. List rows have 20 vertical padding.
- **Radius:** 6 (chips), 8 (controls), 12 (menus), 14 (sheets, on every width, and dialogs), 16 (Home's clock card on phones).
- **Elevation:** a sheet is raised a hair in light (`--raise`, a faint shadow) and not at all in dark; `--lift` for dialogs, menus and popovers only.
- **Sheet padding:** rows and the first and last cells of a table keep 18 from a sheet's sides (14 on phones): `--size-gutter`, class `px-gutter`. A padded sheet (a form, text) has 20 all round (16 by 14 on phones). See rule 10.
- **Content width:** 1240 at most; 1400 on screens from 1600 wide and 1560 from 2200 wide, so a big screen is not mostly empty (`--size-content`). The Students page grows further (1680 from 1600 wide, 2040 from 2200), so the board's five columns need no sideways scroll; it is as wide for the List as for the Board, so the Board / List switch stays under the pointer when it is pressed (ticket 25). The page is marked wide from an effect while it is the one shown (`useWidePage`, a mark on `<html>`), never in its own markup: Next.js keeps the page just left hidden in the background, and markup there went on stretching Applications and Visas opened after Students. Where there is no board it is an ordinary page. Line length under 75 characters for prose.
- **Page margin:** 26 on each side of the page content, beside the sidebar and on tablets (was 40 until 2026-11-14). 16 on phones (see Phones). The safe area of a phone with a notch is added on top.

### Sheets

Replaces "Lines" (ticket 21; the 2px line under a section title and its "no line after tabs or figures" rules are gone).

- **A section's content is a sheet** (`ui/Panel`): `--paper`, a 1px border (`--sheet-rule`), 14 corners and a faint shadow in light, none in dark. The page is a little deeper (`--canvas` light `#f6f3ed`) so sheets stand off it. The section title sits above the sheet, 10 from it.
- **Between rows:** 1px `--rule` (ink 15% light, 17% dark).
- **Tables:** column heads sit on a faint band (`--band`), 42 tall, in `--ink-2`, with a line under them. A row that opens something shows a soft fill (`--row-hover`) under the pointer, never under a finger.
- **Tablets (641 to 1024):** a table's cells sit closer (8 on each side; the first and last keep the sheet's padding) and a cell that does not shrink may take two lines (a date), so no table runs past its sheet.
- **Figures** (`TileGrid`) are one sheet with thin lines between the figures only, right at any number of columns: the first figure of a row has no line on its left.
- **Dark:** a card that stands on a tinted column (the Students board) is a step lighter than the column.
- **Settings** has no subtitle.

### The thread

A Student's journey is five beads on a string, Lead to Visa, each a shade deeper, light green to dark green (owner, 2026-11-27; until then they were shades of the burgundy accent): the good green (`--good`) mixed into `--paper` at 30, 47.5, 65, 82.5 and 100% (dark: 44, 58, 72, 86 and 100%), as `--bead-1` to `--bead-5`. The tick on a done step is dark on the three lighter shades (`--bead-3-ink` for the middle one, dark in both modes) and `--accent-ink` on the two deepest. "Where is this Student" looks the same everywhere:

- **In a list** (`ui/Thread`): the Stage's name, then the beads. A bead reached is filled in its shade and joined to the next by a string of that shade; the current bead has a ring (a 2px gap, then 2px in its shade) that is never cut off by what holds it; the rest are hollow on a grey string. A granted Visa fills all five; a Lost Student has none marked.
- **The Students list's Stage column** (`ui/StageMeter`): five small dots in the same shades, hollow when not reached, then the name. On phones only the name is shown, with no dots (owner, 2026-11-27). In a narrow cell the name is cut with "…" and the dots stay.
- **A Student's page** (`ui/Journey`): a done step is filled in its shade, the current one ringed in it.
- **The board's column heads** carry their Stage's bead.
- Screen readers hear "Stage: Offer". The colour never stands alone: the Stage's name is always beside the thread.

## Components

Build each once in `src/components/ui`, with tests, and reuse them. Screens never restyle a component.

- **Button:** primary (one per screen area, filled burgundy), secondary and ghost (words in `--ink-2` with an icon, no box, a soft fill on hover), danger (red words, no box); sizes small, default and large, all 44 tall; side padding 12 (16 for the main button, 10 small; 14 and 10 on phones); icon-left optional; disabled and loading states. A button in a table row stays in its cell, right-aligned, on computers (Accounts "Details", Employees "Manage", "Send the code again", "Cancel invite").
- **Field:** label always visible, optional hint, error text below. Wraps text, email, tel, date, number, select and textarea.
- **Segmented control:** two to five choices that switch a view (Light/Dark, New/Returning visitor, report picker), drawn as words with an underline: the chosen one in `--ink` over a 2px accent line, the others in `--ink-3`, with a 1px line under the strip. It is a tab strip: it never wraps onto a second line. On phones it fills the width and scrolls sideways (no scrollbar) when the choices don't fit. On every width, when the strip is drawn after a choice, it scrolls so the chosen one is in view, centred where possible, and never jumps back to the first; this happens once per drawing, so a later small update (the clock timer, typing) never moves a strip the person has swiped. Tabs and the settings section strip on tablets follow the same rule. A choice of one value (Attendance: Present / Absent / Late / Leave) fills the width with equal buttons on one line on phones.
- **View switch** (`ui/ViewSwitch`, ticket 08): two ways to see the same things (Board or List; Calendar or List). A small pill on a quiet fill, each choice an icon and a word, 44 tall; the chosen one is raised on white. It is the one switch drawn as a pill: it changes how a list is drawn, not what is shown, and sits at the right end of its own row. The choice is remembered on the device.
- **Segmented choice:** one value from a few, as a radio group drawn like a pill (Attendance, Priority, a reason). On phones up to four choices are equal buttons on one line; five or more wrap onto more lines, so their words never overlap (ticket 20).
- **Tabs:** sections of one record (Student profile), words with an underline like the segmented control; a count is a quiet number after the word, not a pill.
- **Panel:** a section's content for lists, tables and forms: a sheet (see Sheets). A section title sits above the sheet, not inside it.
- **Row item:** title (a name, `text-name`), secondary line, right-side actions or status. The standard list row. A marked row (the Chosen Offer) has a 3px good line drawn on its left edge and a faint good tint; its text keeps the sheet's padding, in line with the rows around it.
- **Chip:** status with a 7px dot and a word in the status colour, no filled badge. Colour comes from the status, never from the theme: an in-progress status is ink with a hollow ring (rule 3).
- **Progress bar:** 12 high, green (`--good`) whether done or not, with the percentage written next to it.
- **Thread:** a Student's Stage in a list, as five beads (see The thread).
- **Journey:** Lead → Counselling → Applying → Offer → Visa (Onboarded and Completed are gone), its steps in the thread's shades. A Granted Visa ticks the last step ("Visa ✓ Granted"); there is no country or plane at the end of the bar. A Lost Student shows the Lost Stage with its reason. For a Student who was ever Lost, a small ⓘ button sits next to the Stage name: on hover, keyboard focus or tap it shows when they were Lost (with the reason) and when they came back. It is a real button (44 target), never hover-only. Across the panel above 640px (scrolling inside its panel if it must, never widening the page). At 640 and below it is the five Stage names in a row, in 12, with no dots and no line between them (owner, 2026-11-27): the current Stage is in bold with a 2px accent line under it, the ones before it in `--ink-2` and the ones after in `--ink-3`; never top to bottom. A Stage that can be clicked has a 44 tall target.
- **Note:** fixed note colour with a 3px note line on its left, no outline. On a Student's page it is above the tabs; from 1280 it is in a column of its own beside them (see A Student's page), rounded like a sheet with its note line along the top.
- **Banner:** info, warning or problem message across the page.
- **Figure tile:** label, big number, one-line footnote. No card of its own: the figures of a row share one sheet (`TileGrid`) with thin lines between them, never before the first of a row; on phones no side lines. Money: "NPR" is a small label in front of the amount on the same line (smaller, lighter, never wrapped onto its own line); a big number shrinks a little to fit a narrow card rather than touching its edge.
- **Dialog:** title (dialog title size), body, footer with the actions on the right. Only the body scrolls, on every width (ticket 23): the title and the footer stay in view, and above 640 a thin line (`--rule`) sits above the footer, with no fill. Drawing a dialog again keeps the body's scroll (rule 8). Its content keeps the sheet's padding from its sides. Escape and the close button both close it. Focus goes to the first field. On phones it is a bottom sheet (see Phones). The email writer lays out its own body and its footer has no line.
- **Confirm dialog:** one shared dialog for every delete or remove in the app; nothing is removed without it. The title names the thing ("Remove the Grade 12 Transcript?"), the body says what will happen, and the footer has Cancel and a red button that names the action ("Remove", "Delete", "End session"), never "OK" or "Yes". Focus starts on Cancel; Escape cancels. Where a delete needs a reason (a Document put in the Bin), the reason is asked in the same dialog: quick picks plus "Other" with a text box. A Document with several files is deleted from one **Delete** (no trash icon beside a file): the dialog lists its files under "Which files?", all ticked, with "All of them deletes the whole Document. Untick the ones to keep."; with none ticked nothing is sent and it says "Tick at least one file to delete." (ticket 11). Removing a row on an edit page that saves later (Edit details, a University's edit page) needs no popup: the row is only marked, with Undo, until Save. The same dialog asks before something final that is not a delete: marking a Visa Granted or Refused, from its status list or its letter (ticket 10). Its title is "Mark this visa as Granted?", the body says it can't be changed later and that a new try is a new visa application, and the button names the action ("Mark as Granted" filled, "Mark as Refused" red). Cancel leaves the Visa at Applied; over the letter popup, Cancel comes back to it with the file and the choice kept. Once decided, the Visa's Status is a chip with its word, not a list, and the letter popup only takes the file.
- **Menu:** the "More" menu for rare actions. Destructive items sit last, in red. On phones a menu in a page's action row (Priority and More on a Student's page) opens under its button from the left of its row and is never wider than the screen less 32, so it stays on the screen (ticket 23; `MenuList isInRow`). Your menu in the top bar keeps to the right edge.
- **Switch and tick box** (ticket 23): the words are page text. A switch's name is weight 500 and its explanation sits under it in small text (14) in `--ink-3`. A tick box is 20 and never shrinks beside long words.
- **Activity timeline:** a vertical line, newest at the top. Each Stage change is a big dot on the line with the Stages in bold ("**Counselling → Lost**") and the reason, if any, on the line underneath. The line between two Stage dots carries the time spent there ("12 days in Counselling"); the top dot says "in Applying for 5 days so far"; one line above the timeline gives the total ("2 months 4 days since they became a Lead"). Other entries (Payments, Note edits, Visits, Emails) are small dots along the line with their time. Lost and Came back (Lost → Counselling) rows get a mild background (a soft red from `--bad`, a soft green from `--good`, a few per cent strength) and a small tag with the word ("Marked Lost", "Came back"), so the colour never stands alone. Screen readers hear the entries in order; reduced motion is respected.
- **Toast:** confirms an action, using the same verb as the button ("Save visit" → "Visit saved").
- **Empty state:** says what is missing and offers the next action.
- **Error pages** (`errors/ErrorScreen`; owner, 2026-11-27): one page for when the app can't show what was asked for, in the middle of the window on a sheet 14 round: an optional code large and quiet ("404"), the title, one sentence of what to do, and the ways on, the main one filled. **An address that doesn't exist** says "We can't find that page" with **Go to Home** (Go to the Platform under `/platform`) and **Go back**; it no longer takes the person to Home by itself. **A screen that failed** says "Something went wrong." as an alert, with the reference to quote when there is one, **Reload the page** (a full reload, which is what clears it) and **Go to Home** (a plain link, so it opens with a full load). Both show logged out too.
- **Settings pages:** Configuration (office-wide, Admins only), a person's own Settings, the Platform account and a Student's Edit details show one section at a time, on every width, from one shared section menu. Above 1024 the menu is on the left with only the chosen section beside it. From 641 to 1024 the menu is a sideways strip above the section that keeps the chosen section in view (the segmented-control rule). At 640 and below it is the iOS Settings pattern: the page opens on a list of sections (rows at least 56 tall, with arrows); tapping one shows it alone with "← All of {page}" ("← All sections" on Edit details) above it, and arriving at the page always starts at the list. Configuration's sections are General, Documents, Working hours, Exports and Platform controls (tickets 96, 97; Email and SMS removed 2026-11-19, ADR 0023).
- **Side menu** (the Journey frame, ticket 05): above 1024 a strip 112 wide that is always there (it no longer collapses). The office's mark (logo or initials, 48) is at its top; a logo that carries the office's name is too wide for the strip and sits in the top bar instead. Each page is an icon with its label under it (13 on a 16 line, weight 500), 66 tall with 12 corners; a long label takes two lines. The open page is in the accent colour, weight 600, on a soft fill (`--side-active`), with no line beside it. ## Gestures

Gestures are extra ways to do what a button already does; every button stays, for the keyboard and screen readers. The gesture rules are pure functions with unit tests (thresholds, direction, starting point, off conditions). With "reduce motion" on, everything snaps or switches without animation. A plain mouse wheel never triggers a gesture; telling a touchpad (small smooth steps) from a mouse wheel (fixed steps) is a best guess, and when unsure nothing happens. The browser's own swipe back and forward is turned off inside the app on phones and tablets only (1024 and below), where a finger from the left edge opens the menu; on a computer a sideways touchpad swipe is left to the browser (back and forward), and the app never takes it (ticket 19). The Back button and keyboard shortcuts always work.

- **Side menu swipe.** On phones and tablets (1024 and below), a finger swipe right from the left edge opens the slide-out menu and a swipe left on it closes it; the menu follows the finger and snaps back if let go less than halfway. A swipe that starts over something that scrolls sideways (a wide table) scrolls it instead. Above 1024 the side menu has nothing to open or collapse (ticket 05), so a sideways touchpad swipe does nothing to it and goes back or forward, as in any website.
- **Swipe between pages.** Off unless the person switches it on in their own Settings → Preferences ("Swipe between pages", only for them, on every device; moved from Configuration on 2026-11-17; off at first because pages changed by accident). When on, on the main sidebar pages, pulling past the bottom of the page goes to the next page in that person's own sidebar, and pulling past the top goes to the previous one. The page itself slides with the finger or touchpad like a rubber band (easy at first, firmer further out). The gap it opens is a little darker than the page, the page's moving edge has a soft shadow, and the gap says what will happen: "↓ Keep pulling to go to Students", then "Release to go to Students", with the product's logo (40) under the words. The logo turns with how far the page has moved on screen, not how far the finger or touchpad went: 3 degrees for each pixel of the gap, so it slows as the page resists and turns back as the page returns (clockwise when pulled down, the other way when pulled up). It grows from a small flower to full size by the point where letting go changes the page. It is updated in place, never drawn again, so it turns smoothly; with "reduce motion" on it neither turns nor grows. Nothing happens until release; pushing back before release cancels. On release the page slides away in the pulled direction and fades (about 0.2 s), and the new page slides in from the other side and fades in (about 0.3 s). At the first page (Home) the top pull does nothing; at the last page the bottom pull does nothing and shows no hint.
  - Only on purpose: the page must already be resting at the top or bottom for about 0.8 s (was half a second until 2026-11-16) before the gesture starts. A scroll, or its momentum, that runs into the end always stops there and never changes the page; a touch swipe must start while the page is already at the edge; a touchpad gesture is one burst of wheel events, and only a burst that began at the edge can pull. A very long pull passes the threshold: 360 of two-finger scrolling or 480 of finger travel, by which point the rubber-band page has moved about 210 (lengthened on 2026-11-16 from about 80 and again on 2026-11-17 from about 145, because pages still changed by mistake); the page never moves more than 300. One gesture pulls one end only: on a page too short to scroll, going back past where it started cancels instead of pulling the other end. The page and the gap ease after each scroll step (0.15 s) and close together (0.2 s) when let go early. On a short page the page area still fills the screen, so the bottom gap opens at the bottom of the screen, never under the content.
  - Off while editing: a dialog is open, an edit page or the Note is open, there are unsaved changes, or a field has focus. Filter bars do not turn it off. Off on detail pages such as one Student.
  - There is no pull to reload: arriving on a page always loads its data fresh.

### Movement

Ticket 22. Calm movement, for a tool used all day. Movement says what happened: a page came, a popup opened, a row changed. Nothing moves for show.

- **Short and small.** 100 to 300 ms (a board card that crosses the board takes 320), 5 to 8 px, and only `transform` and `opacity` move (the one exception is the wash on a changed row, a colour that clears). One curve for what arrives (`cubic-bezier(.2, .8, .2, 1)`) and one for what leaves (`cubic-bezier(.4, 0, 1, 1)`). No bounce, no spin.
- **One place for times.** The `--move-*` and `--curve-*` tokens in `globals.css` (classes `ease-arrive`, `ease-leave`, `duration-(--move-…)`), with the same values in `lib/motion/timing.ts` for code; a test keeps them equal, and another fails when a component or the stylesheet writes a time of its own (only the loading mark has its own).
- **Nothing moves because it was drawn again.** Each movement waits for a mark set when the thing really happened (`data-arrive` on the page, `data-move` on what opens or changes, `data-leaving` on the copy of what closes). The rules that decide are pure functions with unit tests (`lib/motion/rules.ts`), like the gestures: when a page counts as arrived, which rows count as new or changed, where a marker starts from, and that less motion turns all of it off.
- **A page arrives:** its blocks rise 6 and fade in (0.3 s), 40 ms apart, four steps at most; then the first 14 rows of each list follow, 18 ms apart. Only when another page opens (or the first one): a tab, a filter or a page of a list noted in the address is the same page, and an action on it never replays the arrival. After a pull between pages the page slides as a whole instead (see Swipe between pages). A block that sizes itself to the window (the Inbox) only fades.
- **The same page (rule 8):** nothing moves the page. A row that is new or changed fades in under a soft wash of `--tint` that clears in about a second: six rows at most at once, and never a list drawn for the first time or redrawn whole (another page of it, another tab). What a tab or switch shows fades in (0.18 s); the strip and everything above it stay still.
- **The marker of where you are slides** (0.25 s) from its old place to its new one: the shade behind the open page in the side menu, the tinted pill in the phone tab bar, the underline of Tabs and the segmented control, and the raised pill of Board / List and Calendar / List. Each is one element of its own (`data-marker`) drawn in the chosen one.
- **Things that open and close:** a dialog fades in and rises 8 with its shade (0.22 s) and leaves in 0.14 s; on phones a sheet rises from the bottom (0.28 s) and sinks back (0.2 s); a dialog that takes another's place (the steps of a board move) only cross-fades. Menus and small panels (More, your menu, the bell, More filters) open from their button (0.15 s). The toast rises in and fades out. The slide-out menu comes in (0.25 s) and goes back (0.2 s), carrying on from where a finger left it, and its shade fades in. **What closes is gone at once:** a copy of it fades out in a layer nothing can touch, hear or focus, so the page underneath is usable (and the cursor back on its button) as soon as it starts leaving; the copy is removed when its fade ends.
- **The Students board:** after a move the cards glide to their new places (0.24 s; 0.32 s for the one that changed column), and the moved card is ringed in the accent for a second.
- **Light and dark:** one cross-fade of the whole screen (0.22 s) where the browser supports view transitions; otherwise the switch is at once.
- **Touch and hover:** colours ease (0.15 s); a pressed button gives a little (scale .97, on every width, never while disabled); the top bar gains a soft shadow once the page is scrolled.
- **Less motion:** with the device's "reduce motion" on none of this runs, and everything switches at once. Loading marks only turn slowly, as before.

## Keyboard

- In any text box of several lines (the Student's Note, reasons in dialogs, the Inbox), Enter makes a new line and Ctrl + Enter (⌘ + Enter on a Mac) saves or submits the form. A small hint beside the Save button says so ("Ctrl + Enter to save"), and the text box is described by it for screen readers. Typing in another language (text composition) never submits.
- Escape cancels editing the Note, as it closes dialogs.
- In the Inbox, Enter sends and Shift + Enter makes a new line.
- One shared hook does this for every multi-line text box; screens never handle these keys themselves.

## Screen sizes

Every screen is checked at 1440, 1024, 820 and 390 pixels wide.

- **Above 1024:** the side menu (a strip 112 wide) plus content, 1240 at most (more on wide screens, see Content width), with the search centred over the content.
- **1024 and below:** single column with the slide-out menu (opened by ☰ or a swipe from the left edge) and the search icon in the top bar. Two-column layouts stack. Progress rows put the document button beside the name and the bar underneath.
- **640 and below (phones):** everything in the Phones section below. The top bar keeps the office's mark and icons only (search, notifications, your initials) and the tab bar replaces ☰. Lists keep only what matters and every other table shows as cards, never scrolling sideways; only a chart scrolls sideways inside its own panel.
- **Scrollbars are hidden** everywhere (`scrollbar-width: none` and `::-webkit-scrollbar`). Content still scrolls with the wheel, touch and keyboard.
- **Tables fit their panel** (asked 2026-11-17). A list table never scrolls sideways because of a long name: its main text (the Student's name, the university and course, an employee's name and email, a payment's purpose) stays on one line and is cut with "…", with the whole text on hover and for screen readers, while short columns (dates, Status) keep their full width. A table with many columns (Applications and Visas, seven each) keeps every column as a table: the Student, the university or country and the counsellor each get a fixed share of the width and are cut with "…", cells have 12 side padding, and a date or intake may wrap onto two lines when it is tight. Every other table fits too: Reports → Staff Progress cuts the name with "…" and wraps its headings, and a Catalogue card's course table has no minimum width (intakes and documents wrap). Only a chart scrolls sideways, inside its own panel. In code: `DataCell shrinks` (or `shrinks="small" | "medium" | "large"` with `DataTable wraps`; a row heading cell takes `data-shrinks` too) with `OneLine` inside.
- **No horizontal page scroll at any width.** Anything wide scrolls inside its own box: every grid or flex child that holds one has `min-width: 0`, so it can shrink below its content. Touch targets are at least 44px, with no exceptions for "small" sizes.

## Phones (640 and below)

Decided 2026-11-16, after the product owner reviewed the prototype on a phone ("the mobile version is not nice at all and not friendly"). Phones follow the common rules of Apple's Human Interface Guidelines and Google's Material 3, so the app feels native, not like the laptop layout shrunk down. The reference is the phone blocks at the end of the product docs' `docs/prototype/first/crm-demo/styles.css` and the product docs' `docs/prototype/first/crm-demo/mobile.js`. Nothing in this section changes anything above 640, apart from tab strips keeping the chosen tab in view.

### Shell

- **Bottom tab bar:** Home, Students (Classes for a Teacher), Tasks, Inbox and Menu, each only if the person's sidebar has it. Menu opens the slide-out side menu. Badges show the same counts as the side menu. The current page has a tinted pill (`--tint`) behind its icon and the accent colour on its word; on pages that aren't in the bar, Menu shows as current. It respects the phone's safe area, and the page leaves room under its content for it.
- **Top bar:** 60 tall, with no ☰ (Menu replaces it), no office name (only the office's mark: the name is at the top of the menu) and no light/dark button (it moves to the foot of the side menu). Search, notifications and your initials stay.
- **Translucency:** the top bar and the tab bar are slightly see-through (the panel colour at 88%) with a blur behind them.

### Sizes and look

- **Layout:** 16 side margins and an 8 spacing rhythm.
- **Type scale:** one step smaller than on computers (see Type): page text 15, names 16 (Email names 18), sub-lines and chips 14, small text and column heads 13, table cells 15, page titles 24, section titles 18, Note text 15 / 23, Settings rows 16, buttons 15 with 14 side padding (small 14 / 10), figures 24, Pipeline counts 20, a Student's name 22 with a 52 avatar. Fields stay 16. Secondary text uses `--ink-2`.
- **Touch targets:** every tap target is at least 44 tall. Fields are 48 tall with 16 text, so phones never zoom in on them.
- **Sections:** a sheet, as on computers, with 14 inside its sides.
- **Feedback:** everything tappable has a pressed state (a `--fill` background on rows, a slight shrink on buttons).

### Page actions

Ticket 06 (was: the main action full width on top, 48 tall).

Priority and the actions share the next line, which wraps: Priority is a small pill (14 text, still 44 tall), the main action (Take a payment, or Assign a counsellor) the same compact pill as on other pages, the rest small text buttons.

- Segmented controls, Tabs and the settings section strip stay on one line, fill the width and scroll sideways (no scrollbar) when they don't fit. The chosen one is kept in view (see Segmented control).
- Attendance (Present / Absent / Late / Leave) is four equal buttons on one line.

### Dialogs

- The content scrolls; the header and the buttons stay in view. The buttons share the width.

### Lists, filters and busy boxes (ticket 95)

- **Filters** (ticket 06; was a row of pills): a list's filters fold behind one button. Beside the search it is a 44 square outlined button with the sliders icon; where a list has no search it says "Filters" and sits on its own line at the right. ## Theming

### One theme: Ivory

Every office shows the same theme, Ivory (owner, 2026-11-24): almost white, burgundy only where it matters, the menu part of the page. Each Staff member chooses light or dark for themselves (stored per person); nothing else about the colours is chosen. The office logo still shows in the menu and on the login screens.

| Token            | Light                                                                                   | Dark                       |
| ---------------- | --------------------------------------------------------------------------------------- | -------------------------- |
| `canvas` (page)  | `#f6f3ed`                                                                               | `#121110`                  |
| `paper` (panels) | `#ffffff`                                                                               | `#1a1817`                  |
| `fill`, `fill-2` | `#f4f1eb`, `#ece7df`                                                                    | `#211f1d`, `#292624`       |
| `ink`            | `#1f1916`                                                                               | `#f1e8dd`                  |
| `ink-2`          | `#625750`                                                                               | `#bcae9f`                  |
| `ink-3`          | `#766c65`                                                                               | `#8f8174`                  |
| `accent`, hover  | `#6e1a26`, `#57141e`                                                                    | `#d98a8f`, `#e7a2a6`       |
| `accent-ink`     | `#ffffff`                                                                               | `#1d1012`                  |
| `tint`           | `#f3e6e3`                                                                               | `#3a1d1f`                  |
| `rule`, `rule-2` | ink 15%, 26% into the panel                                                             | ink 17%, 27%               |
| Menu (`side-*`)  | the page colour, page text, `fill` hover, `fill-2` for the open page, no line beside it | the same from the dark set |

### How it becomes tokens

A pure function `buildThemeTokens()` in `src/lib/theme` returns the `{ light, dark }` token maps (`ivory.ts` holds the values). It is unit-tested. The same values are written in `globals.css` for the first paint, and a test keeps the two equal. The shell writes the tokens onto `<html>` when it loads and again when the person switches light or dark. The function takes nothing: there are no office colours to pass in (removed in ticket 04), and emails use the same burgundy (`#6e1a26`).

### Tests the function must pass

- The Ivory values, light and dark, as in the table above.
- Every text token (`ink`, `ink-2`, `ink-3`, `accent`) at least 4.5:1 on `paper` and on `canvas`; `accent-ink` on `accent`, the menu text on the menu, at least 4.5:1.
- Lines at the documented mixes; every token a six-digit hex, so nothing else can reach the page's CSS.

## Enforcement

- A lint check (a custom ESLint rule or a CI grep) rejects hex/rgb/hsl literals and Tailwind arbitrary colour values outside `src/lib/theme` and `globals.css`.
- A component test renders each `ui` component in Ivory light and Ivory dark.
- New screens are reviewed against this page before merging.
